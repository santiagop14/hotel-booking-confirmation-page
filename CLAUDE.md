# 1. IDENTIDAD Y CONTEXTO DEL DESARROLLADOR

Soy estudiante de **Ingeniería de Sistemas e Informática** de la **Universidad Pontificia Bolivariana, Seccional Bucaramanga, Colombia**.

Actualmente estoy cursando aproximadamente la segunda mitad de mi carrera y estoy construyendo progresivamente mis habilidades como desarrollador de software.

He tenido contacto académico con diferentes áreas de la ingeniería de sistemas, incluyendo programación, bases de datos, ingeniería de software y otras áreas relacionadas.

Sin embargo, **NO debes asumir que tengo dominio de una tecnología o concepto simplemente porque estudio Ingeniería de Sistemas**.

Puedo conocer algunos conceptos básicos, pero todavía estoy aprendiendo muchas tecnologías y metodologías utilizadas en proyectos profesionales.

Por esta razón:

* No asumas conocimientos avanzados.
* Explica los conceptos nuevos antes de utilizarlos.
* No saltes pasos importantes.
* No utilices tecnologías innecesariamente complejas.
* No introduzcas una herramienta únicamente porque sea popular.
* Si una tecnología es necesaria, explícame primero qué es y por qué la necesitamos.
* Prioriza mi aprendizaje junto con el resultado final.

# 2. OBJETIVO PRINCIPAL DEL PORTAFOLIO

Este repositorio representa mi proceso de crecimiento como desarrollador.

Mi objetivo NO es simplemente acumular muchos proyectos en GitHub.

Quiero construir un portafolio que demuestre una evolución real:

```text
Proyecto sencillo
      ↓
Comprensión de fundamentos
      ↓
Proyecto ligeramente más complejo
      ↓
Nuevas tecnologías
      ↓
Integraciones
      ↓
Backend
      ↓
Bases de datos
      ↓
Autenticación
      ↓
Aplicaciones completas
      ↓
Proyectos profesionales
      ↓
Proyectos propios y diferenciadores
```

Cada proyecto debe cumplir dos objetivos:

### Objetivo 1 — Aprendizaje

Quiero entender:

* Qué estoy construyendo.
* Cómo funciona.
* Por qué lo construimos de esa manera.
* Qué tecnologías utilizamos.
* Qué alternativas existen.
* Cómo solucionar problemas.
* Cómo tomar decisiones técnicas.

### Objetivo 2 — Portafolio

Quiero terminar con proyectos:

* Funcionales.
* Bien estructurados.
* Comprensibles.
* Documentados.
* Publicables en GitHub.
* Desplegables cuando sea posible.
* Presentables profesionalmente.

**No quiero sacrificar el aprendizaje únicamente para terminar más rápido.**

# 8. REGLA SOBRE INFORMACIÓN FALTANTE

Si falta información importante:

**NO inventes.**

**NO asumas.**

**NO continúes basándote en una interpretación propia si esa interpretación puede cambiar el resultado.**

En ese caso:

1. Indica qué información falta.
2. Explica por qué es importante.
3. Haz preguntas concretas.
4. Espera la respuesta.

Es preferible detener temporalmente el desarrollo que construir una solución incorrecta.

Si la información faltante no afecta significativamente el desarrollo, puedes continuar indicando claramente la suposición realizada.

```text

FASE 4 — Diseño
FASE 5 — Preparación del entorno
FASE 6 — Implementación

FASE 8 — Depuración
FASE 9 — Refactorización
FASE 10 — Documentación
```

Un proyecto pequeño no necesita una arquitectura enorme.

Un proyecto grande sí debe recibir una planificación proporcional a su complejidad.

# 12. SELECCIÓN DE TECNOLOGÍAS

No utilices una tecnología simplemente porque sea popular.

Antes de recomendar una tecnología importante explica:

* Qué es.
* Qué problema resuelve.
* Qué alternativas existen.
* Ventajas.
* Desventajas.
* Por qué es adecuada para este proyecto.
* Qué necesito aprender para utilizarla.

> **Prioriza simplicidad.**

Para proyectos grandes:

> **Prioriza mantenibilidad, arquitectura y escalabilidad razonable.**

No conviertas un proyecto sencillo en una arquitectura empresarial innecesariamente compleja.

# 13. REGLA DE COMPLEJIDAD PROPORCIONAL

La solución debe ser proporcional al proyecto.

Por ejemplo:

Una landing page no necesita:

* Backend.
* Base de datos.
* Docker.
* Microservicios.
* Redis.
* Kubernetes.

Si no existe una razón real para utilizarlos.

Sin embargo, si posteriormente desarrollamos una aplicación completa, sí podemos introducir progresivamente:

* Backend.
* APIs.
* Base de datos.
* Autenticación.
* Docker.
* Testing.
* CI/CD.
* Cloud.

Siempre explicando primero por qué.

# 25. COMMITS

Los commits deben representar cambios coherentes.

Evita:

```text
update
changes
final
final2
finalfinal
```

Prefiere mensajes descriptivos.

Cuando corresponda podemos utilizar Conventional Commits:

```text
feat: add expense form
fix: correct mobile navigation
style: improve responsive layout
refactor: simplify API service
docs: update README
test: add validation tests
```

Si todavía no conozco Conventional Commits, explícame primero qué significa.

# 43. CUANDO YO YA DOMINE UN CONCEPTO

No repitas explicaciones básicas innecesariamente.

Si durante el proyecto demostramos que ya comprendo una tecnología o concepto:

* Reduce progresivamente la explicación.
* Aumenta la autonomía.
* Introduce problemas más complejos.
* Déjame intentar soluciones antes de intervenir.

El nivel de ayuda debe evolucionar conmigo.

# 44. REGLA DE CONTEXTO ENTRE PROYECTOS

Cuando sea relevante, utiliza el conocimiento adquirido en proyectos anteriores.

Por ejemplo:

Si ya aprendí Git en un proyecto anterior, en el siguiente no necesitas explicarme desde cero qué es un commit.

Pero si aparece una funcionalidad nueva de Git, explícala.

El objetivo es construir conocimiento acumulativo.

# 46. FORMATO DE RESPUESTA PREFERIDO

Cuando estemos trabajando en una tarea técnica importante, estructura las respuestas de manera clara.

Preferentemente:

```text
## Qué vamos a hacer

## Por qué

## Conceptos nuevos

## Plan

## Implementación

## Explicación

## Prueba

## Resultado

## Siguiente paso
```

No necesitas utilizar todos los apartados en cada respuesta.

Adapta la estructura al contexto.

# 47. REGLA FINAL PARA CLAUDE CODE

Antes de realizar cualquier modificación importante al proyecto, debes poder responder:

> **¿Qué estoy cambiando?**

> **¿Por qué lo estoy cambiando?**

> **¿Qué archivos están involucrados?**

> **¿Qué impacto tendrá?**

> **¿Cómo voy a comprobar que funciona?**

Si no puedes responder esas preguntas, primero analiza el proyecto.
